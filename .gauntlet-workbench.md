# Landing page gauntlet — workbench

Working log for the bounded gauntlet on `/` (`src/pages/index.astro`). One entry
per round: score, largest gap, attempted change, evidence, next action.

**Objective.** A first-time TypeScript developer answers five questions from a
ten-second look at the first viewport — what is it, who is it for, what result
does it give me, why this instead of the alternatives, what do I do next — and
after thirty seconds also knows the supported runtimes, that storage and relay
are the application's, that it is alpha, and where the security boundary is.
Optimise for qualified starts of the ten-minute quickstart.

**Authority order.** The SDK code wins on technical claims. Then
`docs/messaging.md` (banned claims, the fixed relay formula, vocabulary),
`docs/positioning.md` (audiences, limits), `docs/identity.md` (naming
hierarchy), `design/DESIGN.md` and `website/DESIGN.md` (visual contract).

**Boundaries for this run.** Changes are confined to `website/`. Nothing is
committed, pushed, published or deployed. No founder-gated decision is made
here; `docs/decisions.md` §1 keeps final tagline sign-off, the audit
engagement, the named maintainer, and the social preview image open.

## How the evidence is produced

The browser extension cannot resize its window past 900×557 on this machine, so
viewport evidence comes from a headless Chrome driven over CDP:

| Tool | What it produces |
|---|---|
| `scratchpad/shoot.mjs` | Exact-viewport PNGs at 1440×900, 1280×800, 390×844, light and dark, fold and full page. `Emulation.setEmulatedMedia` supplies `prefers-color-scheme`, which is what `public/theme-init.js` resolves `system` against. |
| `scratchpad/probe.mjs` | Measured JSON: contrast ratio of every text-painting element against its effective background, elements painting past the viewport edge, focus ring measured by focusing each control, accessible names, the 200 % zoom equivalent (720 CSS px) and the 320 CSS px reflow floor. |
| `scratchpad/shoot-ref.mjs` | First-viewport captures of the three craft references. |

Critics receive those artefacts, the built `dist/index.html`, the source, and
the test output. No critic grades a summary written by the builder.

### Measured facts that bear on the objective

- **The hero code sample has no syntax colouring.** `HeroSnippet.astro` renders
  `<pre><code>{heroCode}</code></pre>`; Shiki is configured in
  `astro.config.mjs` for markdown only (`github-light` / `github-dark`), so the
  landing page's only code is one flat colour in both themes.
- **The install command is clipped on mobile.** `.code-command > span` is
  `overflow-x: auto; white-space: nowrap` (`global.css:1116`), so at 390 CSS px
  the visible text ends at `npm install @open-e2ee/signal-protocol-` — the
  package name is unreadable without scrolling inside the row. The copy button
  still copies the whole command.
- **The signature diagram does not fit a phone.** `.diagram svg` has
  `min-width: 32rem` (`global.css:789`) inside an `overflow-x: auto` box, so at
  390 CSS px a 512 px drawing sits in a 358 px column: 30 % of it is reachable

  roughly 620 px of a 900 px viewport and nothing follows it in the right
  column.
- **Above the fold the page never names its reader or its result.** The lead is
  a capability list — `Post-quantum PQXDH and the Double Ratchet, multi-device,
  groups, sealed sender, encrypted attachments` — and the comparison that
  answers "why not libsignal" is the fourth band down.

### The defect the overflow check could not see

Re-running the probe after the diagram fix produced a viewport of **528 px on a
390 px phone**. `<meta name="viewport" content="width=device-width">`, with no
`initial-scale`, lets the browser shrink the page to fit its widest element. So
a page that overflows does not scroll sideways — it renders small. And the
check for it, `scrollWidth > innerWidth`, stays false, because `innerWidth`
grew to meet `scrollWidth`.

This had been true all along, and it means **round 0 and round 1 reported the
mobile overflow honestly at the page level and misleadingly at the element
level.** Applying round 2's classifier to their own recorded output:

| Round | Boxes outside a 390 px viewport | Of those, actually painted |
|---|---|---|
| 0 | 13 | **10** — the code block at 33→652, the whole diagram at 16→528, Device B and the `open` label entirely outside |
| 1 | 13 | **10** — unchanged; round 1 did not touch either surface |
| 2 | 2 | **0** |

At 320 px the round 1 figure was 26 painted, including the relay label. The two
that remain at every width are a skip link parked at −9999 and the text inside

and paints nothing. The probe now says which is which, and refuses a whole row

`initial-scale=1` is the fix. Nothing caps `maximum-scale` and nothing sets

those strings in order to say it does not use them.

### The signature diagram: keep, replace, or remove

The brief calls the diagram a hypothesis and asks for three tested choices.

**Option C — remove it.** The page would lose the only place the relay is drawn
rather than asserted. The relay formula is the load-bearing claim of the whole
product and `design/DESIGN.md:403` fixes its wording precisely because it is
easy to overstate; a reader who takes *never needs plaintext* on trust has
taken the central boundary on trust. Removing it also spends nothing it saves:
the desktop page does not get shorter in any place a reader is deciding.
Rejected.

**Option B — replace it with a simpler OpenE2EE-native architecture visual.**

cannot show a sealed thing passing through an open place. Rejected on the
grounds that it is not a simpler version of this drawing, it is a drawing of
something else.

was the fit: 512 px of drawing inside a 356 px column, with the second device

### Corrections to the evidence pipeline

Three defects in the measuring tools, all of which had been quietly inflating

1. **SVG text was graded on `color`.** SVG paints with `fill`; every diagram

2. **`:focus-visible` was sampled after `blur()`**, where it can only be false.

rendered at every width** for four minutes between the edit and the fix.

*alongside* the stacked ones, confirmed by `mq.mjs` reporting `mq48: true` with

### The false guarantee, and why eight gates missed it

`design/DESIGN.md` fixes the wording — *"the relay never needs message plaintext
or device private keys"* — and says not to paraphrase it into an absolute. The
absolute is not a style violation; it is false, and the site says so itself in
the paragraph underneath. The upstream `docs/SECURITY.md` never makes the
unqualified claim: it puts *"recovery of authenticity on unauthenticated first
contact"* in its out-of-scope list, which is exactly the case the absolute
denies.

Three instances shipped anyway, and the reason is worth recording. The rule was
written, reasoned through at length, and then enforced on two SVG files:
`tests/site-content.test.mjs` asserted `doesNotMatch(/cannot read/)` against
`SignatureDiagram.astro` and `WhoHoldsPlaintext.astro` and nothing else. The
build audit's `BANNED` array carried fourteen patterns — *zero-knowledge*,
*military-grade*, *sees nothing* — and none for this one. So the build printed
*"no banned claims"* over three live instances, on the page a reviewer reads
before signing off, in an unaudited alpha.

Both guards now cover it, and neither subsumes the other: the audit greps
rendered HTML and cannot see a string built at runtime; the test reads source
and cannot see wording assembled from parts. Both strip comments first, because
explaining a banned phrase means writing it, and the corrected files now quote
the old sentence above the new one.

The patterns were checked in both directions before landing — they fire on all
three historical strings and a fourth variant, and stay clean on the sanctioned
formula, the diagram label, and the four near-miss sentences elsewhere on the
site. *"A relay that cannot read the data cannot restore it"* in the TLS post is
a restrictive clause defining a class, not an assertion about this relay; the
second pattern allows no gap between the noun and the verb, which is what
separates the two.

- A reader with an unanswered **runtime** question has no above-fold route at

The clause that survived is the disqualifying half. *"Expo and Node are

The alternatives gap is not closed and is not conceded — see *Refused, with the

### Scope is not the same as severity

The type-ramp correction is the case for measuring before adopting a critic's
patch. The proposal was to re-cap the global `h2` clamp from 2.25rem to 1.75rem.

(The proposed patch also read `clamp(1.625rem, 1.25rem + 1.6rem, 1.75rem)`,
substituting `rem` for the `vw` in the fluid term, which would have frozen the
ramp. Transcription, not reasoning — but it is why a patch gets applied from the
file, not from the report.)

## Round 12 — two bugs a score could not have found

The final integration critic scored **47/60** — message clarity 8, action

source.

**A space that existed in the source and not in the build.** The comparison band
rendered `was archived in 2021.@privacyresearch/libsignal-protocol-typescript`.
The `.astro` file has a newline there and looks correct; Astro collapses
whitespace between a text node and a following inline element, so the built page
joined a sentence to a package name. It shipped in the one band whose entire job
is being scrupulous about other people's projects, and it survived every round
because every reviewer who checked that band read the source.

Fixed with an explicit `{' '}`. The guard is general rather than a string match,
because the failure mode is structural: the new test scans `dist/index.html` for
any word character adjacent to a `<code>`, `<a>`, `<strong>` or `<em>` boundary.
One occurrence existed site-wide; there are now none.

**A wall for the ear.** `<p class="carrier-cipher">` held ~420 base64 characters
as plain text, with only the trailing ellipsis hidden. A screen reader announced
every character, with no heading or landmark to escape to, immediately before the
line that already carries the whole meaning: "ciphertext — 3,532 base64
characters, 2,648 bytes decoded, excerpt shown". The probe never caught it
because the blob has fine contrast, a correct reading order and no interactive
role — it is not malformed, it is just unbearable, and nothing I built measures
that.

The blob is now `aria-hidden`, the note is not. Nothing is withheld: a listener
now gets the count, the decoded size and the fact that it is an excerpt, which
is strictly more than they could have recovered from hearing it.

## Round 17 — line numbers, an adapter selector, and no elisions

Three asks in two messages: "lets add lines to the code, also we shoud have tabs
selector or dropdown for relay vs device storage etc", then "we should remove
the ... in the code examples - keep them simple and we shoudl be able to select
the adapter option and then copy the code".

The third one is the load-bearing one, and it is not a styling request. It says
the snippet stops being an excerpt.

### Why the elisions had to take the recording with them

`hero-snippet.mjs` sliced four segments out of `carrier-capture.json` and joined
them with `…`. That is a correct shape for an excerpt: the marks are honest
disclosure about what was cut. The moment a copy button sits on the panel, the
same marks stop being disclosure and become a program that does not run. So
removing them meant removing the gaps, and removing the gaps meant the snippet
could no longer be a slice of the recording.

Then the selector made it stricter still. Every line has to be true for every
adapter offered — and the recorded quickstart drives **both sides of a
conversation in one process**. It calls `relay.registerDevice()` twice and reads
the queue back with `relay.getPendingMessages()`. Both are mock-relay methods.
`convexRelay` returns a different class and has neither. A snippet built by
swapping the relay import of the recording would have compiled in the reader's
head and failed on their machine — the exact failure this site spends its whole
budget avoiding.

So the program became the portable subset — construct, subscribe, send — which
is also what an application actually writes, because an application owns one
side rather than both.

### The provenance claim had to be rewritten, precisely

Old: "every line is lifted verbatim". Measured after the rewrite: **5 of 13
non-blank lines differ**, all for one reason — `alice`/`bob` collapse to one
`signal`, and the comment beside it changes from "only on Bob's device" to "only
on this device".

That is the third time in this loop that a comment's factual claim went stale
under a change, and the second time this session. The rule that keeps working:
say what is *still* exactly true rather than reaching for the stronger sentence.
Imports verbatim; relay construction, identity, adapters line and message string
verbatim; every remaining line matches under that single rename; every method
called is one the recording calls. The test now encodes exactly that — it undoes
the rename and requires each line back in the capture verbatim.

`index.astro`'s caption said "lifted from the quickstart as recorded", which
became false with it, and the link beside it invites the reader to go diff it.
Now: "Send and receive, as an application writes it."

### `syncToServer()` came out

`client.d.ts`: "Called automatically by create() when a relay is configured."
The recording calls it twice because it has two clients to bring up. Keeping it
would have spent a line teaching a call the previous line already made — and a
reader who checks the types finds that out. Dropped, and the reason recorded in
the lib so nobody re-adds it. The fact it carried (your prekeys go to the relay)
is a claim about the model and lives in prose.

### Ten variants, because of the CSP

`script-src 'self'` leaves no room for a runtime highlighter, so a combination
that did not exist at build time could never be coloured. Five stores × two
relays, all rendered at build, nine `hidden`. Verified: 13 focusable candidates
in the panel, **4 actually reachable** — two selects, the copy button, and the
one visible `<pre>`. Shiki puts `tabindex="0"` on every `<pre>`, so nine
unreachable scroll containers in the tab order was the live risk.

`(experimental)` goes in the option text, not beside the control. Two tests hold
both pages to "Browser and bare React Native stores are experimental; Expo and
Node are not", and a dropdown offering all five as peers would be the one place
that sentence is contradicted by the control it describes.

Two options take an object the SDK does not export — `reactNativeStore({storage})`
wants a backend with `atomicWrite` (AsyncStorage does not qualify) and
`convexRelay` wants the reader's own client. Naming a library there would be
invented usage of somebody else's API, the one false-claim class the build audit
structurally cannot catch. Notes say whose object it is instead.

### The line-number gutter surfaced a shipped bug

Light+ and Dark+ carry no `editorLineNumber.foreground` — both resolve
`undefined`, because VS Code composes them with a base theme shiki does not
bundle. There was nothing to quote, and restating VS Code's default from memory
would be a claim this repo cannot check. The numbers are `--oe-muted`: ours,
already measured on both editor surfaces (6.54 / 6.12), now a named contrast row.

mobile-only `display: block` had already been doing. Measured at 390 **before**
any change this round: 23 lines occupying 47 rows, and all four authored blank

anonymous block, while every empty `.line` collapsed. The program had been
rendering double-spaced with its paragraph structure inverted, on every phone,

after: four blank lines at 22px, zero collapsed, at 1440/390/320.

code rather than under the gutter, and it keeps the numbers out of `textContent`

## Round 23 — "seems the syntax highlighting isn't working?"

It was not. Round 22 shipped a hero panel with **zero** syntax colours, and I
reported that round as verified.

### The bug

Round 22 replaced two working rules —

```css
.code-block .astro-code span      { color: var(--shiki-light); }
:root.dark .code-block .astro-code span { color: var(--shiki-dark); }
```

— with an indirection through one custom property, to widen the fix to blog
posts and to pin `.code-block` to Dark+ without a specificity tie:

```css
:root       { --oe-shiki: var(--shiki-light); }
:root.dark  { --oe-shiki: var(--shiki-dark); }
.code-block { --oe-shiki: var(--shiki-dark); }
.astro-code, .astro-code span { color: var(--oe-shiki); }
```

That rests on a claim the comment stated outright: *custom properties substitute
at the point of use*. They do not. A `var()` inside a custom property is
substituted **at computed-value time on the element that declares it**. Shiki
writes `--shiki-light`/`--shiki-dark` inline on the `<pre>` and on every
`<span>` — *below* every element that was declaring `--oe-shiki`. So the
reference resolved against `:root`, found nothing, and computed to the
guaranteed-invalid value. That inherits; `color: var(--oe-shiki)` then fell back
to the inherited foreground.

Measured, not inferred: all 93 spans painted one flat `rgb(212,212,212)`, and
`getComputedStyle(...).getPropertyValue('--oe-shiki')` returned empty at both
`:root` and the span. `distinct 1`.

### Why every gate missed it

This is the part worth keeping. The failure is silent in every channel the round
was checking:

- the stylesheet parses, so the build is clean;
- the rule matches, so devtools shows it applied;
- `astro check` is clean, the build audit passes, 119 tests passed;
- `tests/code-theme` checks `@shikijs/themes`, and `tests/contrast` checks the
  token maths — **both were measuring values that were correct and never
  reached a pixel**;
- the geometry probes measured widths, sizes, overflow and gutter contrast, all
  of which were right.

And I had screenshotted the panel and called it correct. A dark panel full of
monospace text reads as "a code block" at a glance; it takes looking *for*
colour to notice there is none. The lesson is not "look harder at screenshots" —
it is that a claim about CSS substitution semantics is a technical claim, and
this repository's own rule is that technical claims get verified against the
running page rather than asserted in a comment. The comment asserted it. Nothing
read it back.

### The fix

Three rules of strictly increasing weight, each naming a shiki property on an
element that has one:

```css
.astro-code, .astro-code span                       { color: var(--shiki-light); }  /* (0,1,1) */
:root.dark .astro-code, :root.dark .astro-code span { color: var(--shiki-dark); }   /* (0,3,1) */
:root .code-block pre.astro-code,
:root .code-block pre.astro-code span               { color: var(--shiki-dark); }   /* (0,3,2) */
```

The `:root` on the pin selects nothing extra and is load-bearing anyway: it
takes the pin from (0,2,2) to (0,3,2) so it beats the dark-page rule by weight.
Without it the two tie, and the pin survives only because both name
`--shiki-dark` — a fact about today's palette, not a property of the cascade.
That is the same "harmless tie" reasoning that has now cost this file three
rules.

Round 22's two goals both survive: the blog fix stands (`.astro-code` is
site-wide, not scoped to `.code-block`), and the panel is still pinned.

### The guard

`never reads a shiki colour anywhere but the element shiki wrote it on` asserts
the *shape*, not a rule: no `var(--shiki-*)` may appear inside any custom-property
declaration, in any selector. Plus a positive half, because "no custom property
reads them" is also satisfied by a stylesheet that stopped reading them at all —
which is precisely what the broken version degraded to.

Five mutations, each caught: reintroducing the pin on `.code-block` (2 tests),
reintroducing it on `:root.dark` (1), dropping the `:root` weight (1), flipping
the site-wide default (2), and reconstructing the original bug verbatim (2).

### Verified

`distinct 1 → distinct 8`. `import` paints `#C586C0` — Dark+ keyword purple — in
**light** mode, which is the pin working. Home and /product identical in both
modes. Blog correctly follows the page: `#af00db` light, `#c586c0` dark.
120 tests pass, build 17 pages audit-passed, `astro check` 0 errors.
Round 22's geometry is undisturbed: gutter `#898580` = 4.55 in both themes,
`docOverflow 0` at every width.

### Standing consequence

The contrast suite's numbers for the panel were dead measurements for the whole
of Round 22 and are live now. Nothing in them changed; what changed is that they
now describe the page.

## Round 24 — "are we sure the line numbers have become more subtle and more muted?"

Three asks in one message: verify the muting claim, run experiments viewable in

### The muting claim was half true, and the doubt was well founded

Round 22 reported one change that was really two, and only one of them was
visible.

The gutter went 85% → 82% of `--oe-muted` mixed toward the editor surface. On
`#1e1e1e` that is `#8d8983` → `#898580`: about four values per channel. It is

Worse for the ask: at 82% the value was already within 0.03 of VS Code's own
dark line numbers (`#858585`, 4.52 on this exact background, read out of
`editorColorRegistry.ts` where it is registered as `{ dark: '#858585', light:
'#237893' }`). And 82% was the **last AA step** — 81% measures 4.48.

than an implementation, and it went to the owner with the measured ladder and

| weight | colour | ratio |
|---|---|---|
| 85% | `#8d8983` | 4.79 |
| 82% | `#898580` | 4.55 |
| 81% | `#88847e` | 4.48 |
| **78%** | **`#84807b`** | **4.25** |

WCAG 1.4.3's incidental exemption: text that is pure decoration carries no
contrast requirement. Checked rather than assumed — no copy anywhere on the site
references a line number; the only mention is "the ten-line example", which is a
count. The earlier version of the contrast comment argued the numerals are what
a reader points at to say which line broke. That argument is about an editor
someone is working in, not about a seventeen-line quotation nobody can edit.

The floor moved rather than being removed. `tests/contrast.test.mjs` now holds
this row to the 3:1 non-text minimum, and the comment records the full ladder,
who chose the value, and where the new floor bites — **58%**, at 2.96.

Both were written from estimation and then measured:

- "74% and 70% would still pass it. 64% would not." — false. 64% is 3.33 and
  passes; so does 60% at 3.10. The floor bites at 58%.
- "78% of light `--oe-muted` on white is 3.1" — false twice. The light canvas is

`3.25ch → 4.75ch`, which measures **27.3px** at the panel's 18px and 20.5px at

the numerals. That space keeps the column from reflowing as a file crosses 100

## Round 26 — the strip becomes two clusters, and the phone stops shrinking code

Five founder edits in one round: `Compatible with` for the two labelled groups,
then `Works with`; `S3-compatible` → `S3`; the strip moved from `.hero-copy` to
`.hero-grid` so it takes the container's 1132px instead of the copy column's
48rem; marks stepped 24 → 32 → 40px with names at 18px; and the Browser and S3
marks redrawn as B1 (window frame with an address field) and S1 (bucket with a
handle). Three of those broke a measured number written in a comment, and each
was corrected against a browser measurement rather than reasoned about: the wrap
point moved 768 → 900 → 1000 as the marks grew.

### The wrap unit is the claim

`flex-wrap` on a flat list of seven puts the break wherever the seventh name
falls, and at 900px that was after Convex — a row that says the three backends
are unrelated, which is the one thing the strip asserts they are not. The fix is
two cluster containers (4 runtimes, 3 backends) that are themselves flex items,
with the gap between clusters equal to the gap inside them: one line of seven is
visually identical to what shipped before, and the nesting only becomes visible
when it decides *where* the row breaks.

`display: contents` on the inner `<ul>` was the tempting shortcut and is wrong
twice over — it strips list semantics in more than one shipping engine, and it
dissolves the very box that makes the cluster a wrap unit.

Measured: one row at 1000+, two from 960 to 567 (4 + 3, clusters whole), three
at 566–430 (runtimes wrap, backends whole), four at 390–320. No document
overflow at any width from 1440 to 320.

### 768 is a real device, and `max-width` fires there

The mobile code rules were first written as `@media (max-width: 48rem)`, which
matches at *exactly* 768 — where `@media (min-width: 48rem)` also matches and
the disclosure script holds the panel open. iPad portrait would have got an open
panel, no adapter controls and a scrollbar: three behaviours from two queries
that disagree about which side of the line 768 is on.

The file already had the idiom, written for the same defect on the summary
element: `@media not all and (min-width: 48rem)` is the exact complement, not
almost it. Both new rules moved into that block. Verified at 769/768/767 — the
boundary is now clean in one step: 768 open, controls shown, 13px, program fits
exactly (718 of 718); 767 closed, controls gone, 15px, scrolls (747 of 717).

### Fit is not a constraint once nothing fits

The clamp floor of 13px was arithmetic — the largest size that still fits the
program at 48rem. Below the disclosure breakpoint that derivation has no
premise: 91 characters do not go into a 356px column at any size a person reads,
so the panel scrolls either way and the only live question is how small the type
is while it does. 15px is a legibility floor: above the site's own 13.5px for
code quoted in prose, so the page's primary evidence is not also its smallest
code. The scroll costs about 2.1 screens at 15px against 1.8 at 13px — barely

### The gate that replaced the disclosure test

The old test asserted `convex.comment` existed and matched

comment is gone by design, and `ConvexClient` is not a substring of

What replaced it is the rule underneath the old one, which is a fact about the

the program imports it and needs no caption. If nothing does, a comment has to

`ReactNativeKeyValueStorage` is an interface the reader implements.
